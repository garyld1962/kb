# kb — Personal Knowledge Base CLI + Server + MCP

## Purpose

Build a distributed personal knowledge system that lets Gary capture research, notes, URLs, and AI work logs from any machine, and centrally processes them into a semantically searchable knowledge base backed by his existing Obsidian vault.

The design bridges two concerns surfaced in the original Karpathy conversation:
- **Research capture** — fast, low-friction intake from daily work (human or AI-driven)
- **Curated knowledge** — structured, tagged documents that survive as canonical reference

It also adds an **AI Daily Log** feature: per-project append-only logs of AI-assisted work, with nightly automated summarization.

## Design Principles

- **Capture works offline.** Writes never depend on the network. Syncthing delivers to the server for processing.
- **Obsidian is the source of truth.** All state lives as markdown in the vault. kb-server indexes, never owns.
- **Document integrity over chunk convenience.** Qdrant stores chunks for retrieval, but every chunk carries full provenance back to its source document.
- **Local-only infrastructure.** Ollama for embeddings and LLMs, Qdrant for vectors. No cloud dependencies.
- **One repo, shared core.** CLI, server, and MCP share models and schema. Monorepo avoids coordination overhead for a personal tool.

## Scope (v1 vs Follow-on)

Closed via `/prd-validate` interview, 2026-07-08.

**v1 (Definition of Done target):**
- `kb` CLI: `add`, `log`, `readlog`, `status`, `config`
- `kb-server`: filesystem watcher, Inbox pipeline (chunk/embed/index into
  `kb_knowledge`), Log pipeline (chunk/embed/index into `kb_logs`),
  re-indexing (periodic scan, hash-based change detection, rename/deletion
  handling)
- Search API (`kb search`, `kb search --logs`) and Ask API (`kb ask`) over
  both collections
- `_project-registry.md` (format closed below) and the auto-create/warn
  flow for unknown projects

**Follow-on (explicitly not part of v1's Definition of Done):**
- `kb` MCP server (FastMCP tools: `kb_add`, `kb_search`, `kb_ask`,
  `kb_log_entry`, `kb_read_log`)
- Nightly summarization scheduler (00:01 job, per-project summary
  injection, `status: closed` transition, `Daily-AI-Summaries/` rollup)

Rationale: MCP and nightly summarization are both additive layers on top of
a working capture+search core — MCP re-wraps the same HTTP API, and nightly
summarization reads/writes a store that only exists once the log pipeline
is proven. Building the core first means the follow-on phase depends only
on decisions already closed here, not on request-time product choices.

## Closed Decisions

- **Stack:** Python 3.12 (`uv`-managed), FastAPI (kb-server), FastMCP for
  MCP (follow-on), Qdrant for vectors, Ollama for embeddings/LLM
  (`mxbai-embed-large`, `qwen3.5:9b`). No cloud dependencies.
- **Python version:** pinned to 3.12 (`.python-version` / `requires-python`)
  — matches system Python already present on every machine in the fleet.
- **Package layout:** single `uv` package `kb`, submodules `kb.core`
  (shared models/config — single-owner contract), `kb.cli`, `kb.server`.
  MCP (follow-on) joins the same package under `kb.mcp` later.
- **Persistence / source of truth:** Obsidian vault markdown. Qdrant is an
  index, not a store — kb-server never owns data, only derives from it.
- **API contract style:** REST/JSON over HTTP (`POST /search`, `POST /ask`,
  `POST /log/entry`, `GET /log/read`); MCP (follow-on) wraps the same API.
- **Error handling policy:** capture path (CLI → vault) never depends on
  the network and fails loudly on local write errors; processing path
  (kb-server) retries transient failures (Ollama/Qdrant unreachable) with
  exponential backoff and marks `status: embed_failed` rather than
  dropping data; malformed/corrupted input is quarantined to
  `Inbox/_errors/`, never silently discarded.
- **Chunking:** hardcoded constants — 500-token chunks / 50-token overlap,
  markdown headers (H1/H2/H3) as primary split points, sliding window as
  fallback within long sections. Not configurable in v1; revisit only if
  search quality demands it.
- **`_project-registry.md` format:** YAML frontmatter (project → folder
  mapping, status, created date) plus a free markdown body for project
  notes. kb-server reads frontmatter only; auto-create on unknown project
  appends a stub entry and warns the user.
- **Auth:** none for v1. kb-server's HTTP API is LAN-only, unauthenticated,
  matching the existing personal-tool trust boundary of the server/the GPU host.
  Explicitly out of scope, not an oversight.
- **Test gating:** unit tests (frontmatter, chunker, log format, date/range
  parsing) always run, no network. Integration tests (real Qdrant + mock
  Ollama) run behind an opt-in marker/env flag (`RUN_INTEGRATION=1`),
  skipped by default so a plan executor without the GPU host reachability isn't
  blocked. The end-to-end smoke test against live the GPU host services is
  manual-only, documented but not part of the automated default suite.

## System Architecture

Three components, one repo (`~/repos/kb/`):

```
Any Machine (the GPU host, or any laptop/workstation)
  ┌──────────┐     writes      ┌──────────────────────┐
  │   kb CLI  │ ───────────────▶│ Local Obsidian Vault │
  └──────────┘                  └──────────┬───────────┘
       │ search/ask                        │ Syncthing
       │ (HTTP to the server:8090)            │
       ▼                                   ▼
the server                                the GPU host
  ┌──────────────────────┐              ┌───────────┐
  │ Obsidian Vault        │              │  Qdrant   │
  │ /data/obsidian        │              │  :6333    │
  └──────────┬───────────┘              │  (existing)│
             │ watches                   │           │
             ▼                           │  Ollama   │
  ┌──────────────────────┐               │  :11434   │
  │     kb-server         │── embed ────▶│           │
  │  (FastAPI + watcher)  │── store ────▶│           │
  │  :8090 Docker         │              └───────────┘
  │                       │
  │  ◀─── kb MCP (FastMCP, same proc, :8090/mcp)
  └──────────────────────┘
```

### Data flow

1. **Capture** — `kb add` or MCP writes markdown to local vault's `Inbox/`. Offline-safe.
2. **Transport** — Syncthing replicates to the server.
3. **Process** — kb-server on the server watches `Inbox/`, parses frontmatter, chunks, embeds (via the GPU host's GPU Ollama), indexes into Qdrant (on the GPU host), moves file to destination folder.
4. **Query** — `kb search` / `kb ask` calls kb-server's HTTP API on the server (`http://localhost:8090`).
5. **Nightly** — at 00:01 local time, kb-server summarizes yesterday's project logs and generates the cross-project daily AI summary.

## Components

### `kb` CLI (all machines)

Python CLI installed via `uv tool install`. Lightweight, no server dependency for writes.

**Commands:**

| Command | Purpose | Needs the server |
|---------|---------|---------------|
| `kb add [text\|url\|file]` | Write note to local vault Inbox | No |
| `kb add --stdin` | Pipe content into a new note | No |
| `kb log <project> <message>` | Append entry to today's project log | No |
| `kb readlog <project> [--date=... --range=...]` | Read past log entries | No |
| `kb search <query>` | Semantic search over knowledge base | Yes |
| `kb ask <question>` | RAG answer with citations | Yes |
| `kb status` | Vault stats, last sync, server health | Yes |
| `kb config` | View/edit local config | No |

**Config** (`~/.config/kb/config.yaml`):

```yaml
vault_path: /data/obsidian          # or ~/obsidian on laptops
server_url: http://localhost:8090
machine_name: localhost              # for log attribution
default_project: ""                 # optional shortcut
```

### `kb-server` (the server only)

FastAPI service in a Docker container.

**Responsibilities:**
- **Filesystem watcher** (`watchdog`) on `Inbox/` — processes new files within seconds
- **Processor pipeline** — extract frontmatter → clean content → chunk → embed → index in Qdrant → move file to destination
- **Search API** (`POST /search`) — semantic search over knowledge or logs collections
- **Ask API** (`POST /ask`) — RAG: retrieve top-k chunks, synthesize answer via local Ollama LLM (qwen3.5:9b), return with citations
- **Log API** (`POST /log/entry`, `GET /log/read`) — for CLI and MCP
- **Nightly scheduler** (APScheduler) — runs at 00:01 local time

**Qdrant collections:**

| Collection | Source | Purpose |
|-----------|--------|---------|
| `kb_knowledge` | Knowledge/, Archive/ | Research, decisions, reference docs |
| `kb_logs` | AI-Daily-Log/ | Log entries and daily summaries |

Both use 1024-dim vectors (mxbai-embed-large). `kb search` defaults to `kb_knowledge`; `kb search --logs` or `kb search-logs` targets logs.

### `kb` MCP server (the server, same process as kb-server)

FastMCP wrapping the same API. Configured in `.mcp.json` on each machine pointing to the server.

**Tools exposed:**

- `kb_add(content, title?, tags?, project?, destination?)` — capture to inbox
- `kb_search(query, collection="knowledge", limit=10)` — semantic search
- `kb_ask(question)` — RAG answer
- `kb_log_entry(project, message, files?, stats?)` — add to daily log
- `kb_read_log(project, date?, range?)` — read log

## Processing Pipeline

Two separate pipelines:

### 1. Inbox pipeline (non-log documents)

```
1. Detect new file in Inbox/ (watchdog event)
2. Parse frontmatter → id, source_type, destination, etc.
3. Skip if status != "inbox"
4. Compute doc_hash = SHA-256 of file contents
5. Clean/normalize (strip HTML for url source, fix encoding)
6. Chunk content:
   - By markdown headers first (H1/H2/H3)
   - Fall back to ~500-token sliding windows within long sections
   - Each chunk carries: doc_id, chunk_index, header_path
7. Embed each chunk via http://localhost:11434 (mxbai-embed-large)
8. Upsert into Qdrant kb_knowledge
9. Move file: Inbox/note.md → <destination>/note.md
10. Update frontmatter: status: processed, processed_at, chunk_count
11. Emit event to server log
```

### 2. Log pipeline (AI-Daily-Log)

`kb log` writes directly to `AI-Daily-Log/<project>/<YYYY-MM-DD>.md`, bypassing Inbox. The log pipeline:

- On file change, chunk new entries only (delta since last index)
- Embed and upsert into `kb_logs`
- Nightly summarization runs on all yesterday-dated log files, then generates `Daily-AI-Summaries/<yesterday>.md`

### Qdrant payload (both collections)

```json
{
  "doc_id": "01HXYZ...",
  "doc_path": "Knowledge/research/karpathy-kb.md",
  "doc_hash": "sha256:abc123...",
  "doc_title": "Karpathy on knowledge bases",
  "chunk_index": 3,
  "chunk_of": 7,
  "header_path": "Key Insights > Beyond RAG",
  "content": "...",
  "tags": ["research", "llm", "rag"],
  "project": "",
  "source_type": "url",
  "source_ref": "https://...",
  "created_at": "2026-04-12T14:32:00-04:00",
  "indexed_at": "2026-04-12T14:32:15-04:00"
}
```

### Re-indexing

- **Periodic scan** every 30 min to catch direct-in-Obsidian edits
- **Hash-based change detection**: if `doc_hash` differs from last-indexed, delete old chunks (by `doc_id`), re-chunk, re-embed
- **Rename detection**: same `doc_id`, new `doc_path` → update payloads in place
- **Deletion**: file gone → purge chunks by `doc_id`

### Nightly summarization (00:01 local)

```
For each project folder in AI-Daily-Log/:
  Find yesterday's log file
  If status == "active":
    Read entries
    Call Ollama qwen3.5:9b for summary
    Inject between nightly-summary markers
    Update status: closed
    Update frontmatter.entries count

After all projects done:
  Gather summaries + stats from each
  Generate Daily-AI-Summaries/<yesterday>.md with wikilinks
```

## Error Handling

### Capture path (CLI → vault)

Must be reliable. No network calls on `kb add` / `kb log`.

- File write failures raise clearly (disk full, permission, vault not mounted)
- Unknown project name → auto-create folder, warn user, prompt to register in `_project-registry.md`

### Processing path (kb-server)

- Malformed frontmatter → move file to `Inbox/_errors/` with error log; watcher continues
- Ollama unreachable (the GPU host down) → retry with exponential backoff; eventually mark `status: embed_failed`, leave file in Inbox for later retry
- Qdrant unreachable → same pattern
- Corrupted file (binary content) → skip, log, move to `_errors/`
- Partial embedding → `doc_id`-based re-index is idempotent

### Query path (CLI → server)

- Server unreachable → clear message: "kb-server on the server unreachable. Captures still work offline." Non-zero exit code.
- Empty results → graceful empty output
- LLM slow on `kb ask` → stream partial output when possible

## Assumptions

- Syncthing is configured across all machines for the Obsidian vault path
- the server is canonical processing node; if the server is down, captures still work (vault writes are local), queries don't
- the GPU host's Ollama has `mxbai-embed-large` pulled and is reachable on the LAN (`http://localhost:11434`)
- Qdrant on the GPU host (`http://localhost:6333`, existing instance) hosts kb's two new collections
- Ollama on the GPU host also serves `qwen3.5:9b` for summarization and `kb ask`
- If the GPU host is down: vault captures still work; processing pauses (files pile up in Inbox with `status: embed_failed` and retry when the GPU host returns); queries fail with clear error
